### 1.2 Что пришлось изменить при переносе и почему: отличие C# от C++ по устройству

При переносе классов `SkillTemplate`, `WeaponTemplate` и `CharacterTemplate` с C++ на C# изменения затронули не только синтаксис, но и фундаментальное устройство работы с памятью и объектную модель:

1. **Размещение в памяти и время жизни объектов:**
   * В **C++** объекты предметной области (`CharacterTemplate`, `SkillTemplate`) могли инстанциироваться как на стеке с детерминированным временем жизни (вызов деструктора строго на выходе из блока `{}`), так и в куче.
   * В **C#** все типы-классы (`class`) размещаются исключительно в управляемой куче (managed heap). Выход переменной из области видимости не приводит к немедленному уничтожению объекта: память освобождается недетерминированно сборщиком мусора (Garbage Collector), когда на объект не остается сильных ссылок.

2. **Ссылочная семантика переменных и разделение состояния:**
   * В **C++** присваивание `CharacterTemplate a = b;` по умолчанию выполняет побитовое или кастомное копирование объекта (создается второй независимый экземпляр).
   * В **C#** переменная типа `CharacterTemplate` хранит ссылку (адрес) на объект в куче. Присваивание `var heroSecond = heroFirst;` копирует лишь ссылку. Модификация объекта через `heroSecond` мгновенно отражается на `heroFirst`. Для создания истинных независимых копий значений при присваивании в C# используются структуры (`struct CombatStats`).

3. **Реализация композиции при отсутствии деструкторов:**
   * В **C++** композиция выражалась хранением объекта по значению (`SkillTemplate innateSkill;`). Время жизни части физически совпадало с временем жизни целого.
   * В **C#** поле `_innateSkill` внутри класса всегда является ссылкой. Чтобы обеспечить строгое отношение «композиция», класс-целое `CharacterTemplate` сам создает экземпляр части в своем конструкторе (`_innateSkill = new SkillTemplate(...)`) и **не выдает ссылку на этот объект наружу**. Все взаимодействие с навыком идет только через методы персонажа (`PerformAttack`, `PerformUltimate`).

4. **Освобождение внешних ресурсов без деструктора (`IDisposable` и `using`):**
   * В **C++** действует идиома RAII (Resource Acquisition Is Initialization), где освобождение ресурсов (закрытие сессии боя, сохранение логов) происходит в деструкторе автоматически при выходе из блока.
   * В **C#** аналога деструктора с гарантированным временем вызова нет. Для детерминированного завершения ресурсоемких операций класс `BattleSession` реализует интерфейс `IDisposable`. Конструкция `using (var session = new BattleSession(...))` гарантирует вызов метода `Dispose()` в блоке `finally` ровно в момент выхода из области видимости, освобождая ресурс без ожидания сборщика мусора.

5. **Идиоматический доступ к состоянию (Свойства вместо геттеров/сеттеров):**
   * В **C++** для инкапсуляции применялись методы `getBaseDamage()`, `getLevel()`.
   * В **C#** используются свойства с автоматическими геттерами и приватными сеттерами (`public int Level { get; private set; }`, вычисляемое свойство `public double CurrentDamage => BaseDamage * (1.0 + (Level - 1) * 0.08);`). Для строкового вывода переопределен метод `ToString()`, автоматически вызываемый средой при форматировании.

#### Пояснение трех демонстраций памяти:
1. **Ссылки и копии:**
   * Для класса `CharacterTemplate` показано, что `heroSecond = heroFirst` создает копию ссылки на тот же объект в куче (`ReferenceEquals` возвращает `true`). Изменение стаков через `heroSecond` привело к изменению `heroFirst`.
   * Для структуры `CombatStats` показано, что присваивание создает независимую копию на стеке: изменение полей `statsB` не затронуло `statsA`.
2. **Освобождение ресурса без деструктора:**
   * В блоке `using (var session = new BattleSession(...))` объект захватывает ресурс. При выходе из блока среда выполнения гарантированно вызывает `Dispose()`, что подтверждается строкой лога `[-] Журнал сессии закрыт`.
3. **Сборщик мусора:**
   * Объект создается в методе `CreateTemporaryHero` с возвратом слабой ссылки `WeakReference`. После завершения метода обычных сильных ссылок на объект нет, но он продолжает находиться в куче (`TryGetTarget` возвращает `true`).
   * После вызова `GC.Collect()` и `WaitForPendingFinalizers()` сборщик мусора очищает память, и повторный опрос `TryGetTarget` дает `false`.

### 2.3 Пояснение: когда и почему уничтожается каждый объект
1. **Композиция (`CharacterTemplate` и `SkillTemplate`):**
   При выходе из блока `{}` объект `hero` уничтожается на стеке. Сначала вызывается деструктор целого (`CharacterTemplate: Адеир`), а затем немедленно и автоматически — деструктор вложенной части (`SkillTemplate: Врожденный взрыв стихий`). Это доказывает жесткую связь времени жизни при композиции.
2. **`std::unique_ptr`:**
   Объект `Кинжал Тени` уничтожается точно в точке выхода из блока `{}` без вызова `delete`. При передаче через `std::move` исходный указатель `dagger` обнуляется (`nullptr`), исключая возможность двойного освобождения памяти. Массив `shelf[3]` очищается в обратном порядке создания (`Охотничий лук` -> `Посох искр` -> `Клинок новичка`).
3. **`std::shared_ptr`:**
   Объект `Кровавый Пожиратель` живет до тех пор, пока жив хотя бы один владелец. При выходе из внутреннего блока уничтожается копия `secondOwner`, но объект не удаляется, так как `use_count() == 1`. Лишь после вызова `sharedWeapon.reset()` счетчик достигает 0, и деструктор оружия срабатывает синхронно.
4. **`std::weak_ptr`:**
   Объект `Молот Колосса` уничтожается в момент выхода из внутреннего блока, где находился его единственный владелец `tempWeapon`, несмотря на то, что `weaponObserver` продолжает существовать. Слабый указатель не продлевает жизнь объекту. Вызов `lock()` после этого возвращает `nullptr`, что позволяет персонажу безопасно проверить доступность оружия без риска разыменования висячего указателя.
